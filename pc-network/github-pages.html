GitHub Pages: How This Website Was Created

The complete beginner's guide to free website hosting — and the true story of how this very site got onto the internet.

You are reading this on a website that costs nothing to host, needs no server, and is updated by simply saving files. This page explains exactly how that works — and how you can do the same with your own page, step by step, in about fifteen minutes.

What is GitHub Pages?

GitHub Pages is, in GitHub's own words, "a static site hosting service that takes HTML, CSS, and JavaScript files straight from a repository on GitHub, optionally runs the files through a build process, and publishes a website." In plain language: you put files in a folder on GitHub, GitHub puts them on the internet, free of charge. No server to rent, nothing to install, nothing to maintain.

The address always follows the same pattern:

  • Project site (any repository): https://your-username.github.io/repository-name/ — this site lives at https://alexav3atw.github.io/alex0708mylife/
  • User site (a repository named exactly your-username.github.io): the shorter https://your-username.github.io/ — one per account

What Pages can not do: run server-side code. It serves static files — HTML pages, stylesheets, images, small scripts. For a personal site, a hobby page or a blog, that is usually all anyone needs. (This entire website is static files: 20 pages, one stylesheet and a folder of images.)

Path A — start entirely in the browser

This path needs nothing but a GitHub account and a web browser. No software, no terminal.

  1. Create the repository. On GitHub: New repository → give it a name (any name — the name becomes part of your web address) → choose Public → leave the "Add README" and other checkboxes unchecked → Create repository.
  2. Create your first page. In the repository: Add file → Create new file → name it exactly index.html (lowercase — this matters) → type some HTML → Commit changes.
  3. Switch on Pages. Settings → Pages → under Build and deployment choose Deploy from a branch → branch main, folder / (root) → Save.
  4. Wait. The first build can take up to 10 minutes. When it is done, the same Settings → Pages page shows: "Your site is live at https://…" — with a Visit site button.
Where do the HTML files come from?

Every page on the web is an HTML file. If writing HTML yourself sounds like a lot, that is exactly what tools like Claude Code are for: describe the site you want, and the files are written for you — which is how this website was made.

Path B — the Git way (how this site is really made)

Path A is perfect for a first page. But a real site — many pages, images, changes over months — is easier to manage as a folder on your own computer, connected to GitHub with git. Git is a version control system: every change is saved as a snapshot, and any earlier version can be restored at any time. That means you can never permanently break your site — the previous version is always one command away.

The workflow, once, for a new site (with git installed, from your site's folder):

git init -b main
git add .
git commit -m "First commit"
git remote add origin https://github.com/your-username/your-repository.git
git push -u origin main

Then the same two minutes in Settings → Pages → Deploy from a branch → main → Save. And from then on, every update to the site is:

git add .
git commit -m "What changed"
git push

Within about a minute, the live site shows the new version. No re-publishing, no downtime, no extra clicks — the push is the publishing.

The Jekyll thing (small but useful)

By default, when you publish from a branch, GitHub Pages runs your files through Jekyll — a tool for building blogs. For a plain site of your own HTML files this is mostly harmless, with one trap: Jekyll ignores files and folders whose names start with _, . or #. So a folder like _images would simply not appear on your published site. The standard fix is an empty file named .nojekyll at the top of your repository — it tells GitHub Pages to skip Jekyll and publish your files exactly as they are. (This site has one. Practice what you preach.)

Your own domain name

You do not have to keep the .github.io address. In Settings → Pages you can attach a domain you own:

  1. Buy a domain (any registrar, a few euros per year).
  2. Settings → Pages → Custom domain → type it → Save.
  3. At your domain provider, point the domain at GitHub: for the bare domain (example.com), create A records for all four of these addresses:
    RecordTypeValue
    @A185.199.108.153
    @A185.199.109.153
    @A185.199.110.153
    @A185.199.111.153
    wwwCNAMEyour-username.github.io
  4. Wait. DNS changes can take up to 24 hours to spread worldwide — usually it is minutes.
  5. Back in Settings → Pages, tick Enforce HTTPS. GitHub requests a free security certificate for you automatically and installs it — this option can take up to 24 hours to appear.

When things go wrong

  • 404 right after switching on Pages: normal. The first build can take up to 10 minutes.
  • 404 that never goes away: your index.html must be at the top level of the publishing source (the root of the repository, or /docs if you chose that). It must be spelled exactly index.html — lowercase i. (Index.html does not work.)
  • No index.html at all: Pages will also accept index.md or README.md as the entry page. None of the three → 404.
  • Images or styles missing: check the file paths in your HTML — and remember file and folder names are case-sensitive on GitHub Pages.
  • "Mixed content" errors: an HTTPS page refuses HTTP resources. Change every http:// link in your files to https://.
  • Private repository: Pages on a private repository requires a paid GitHub plan, and the site is still visible to the public. A personal site is simplest as a public repository — the files are all public anyway, since the site is.

Stopping it

Unpublishing is just as easy: Settings → Pages → open the menu next to "Your site is live at" → Unpublish site. The site disappears from the internet, but the repository and all files stay intact — publishing again brings it right back. To remove it completely: set the publishing source back to None, or simply delete the repository.

Case study: how THIS website was made

And now the story of the site you are reading — because it used both paths and a few more tricks:

Step 1 The idea

A personal site about personal interests: space, Kuifje, PCs. Public, in English, with chapters that could grow one subject at a time.

Step 2 The files were written locally

Every page is hand-written HTML in a folder on the computer, with one shared stylesheet and a dark theme whose colours were computer-checked for contrast and colourblind-safety before use.

Step 3 The facts were verified

Research agents checked every date, number and name in the Space chapter against NASA, the Smithsonian and Wikipedia — the first review round caught 19 errors, all fixed before publishing. Photos were selected only from legally free sources (NASA public-domain and Wikimedia Commons), downloaded and compressed to 70% size so the site loads fast.

Step 4 The repository was created

An empty public repository named alex0708mylife — exactly Path A, step 1.

Step 5 Pushing, not uploading

From then on, everything went through git: git add ., git commit, git push. About forty pushes built the site — and every single one is still in the history, so any earlier version of any page can be brought back.

Step 6 Two clicks made it public

Settings → Pages → Deploy from a branch → main → Save. Ten minutes later: "Your site is live at https://alexav3atw.github.io/alex0708mylife/".

That is the whole secret. No server, no costs, no maintenance — a folder of files, a push button, and the internet does the rest.

Ready to try it yourself?

Start with Path A and one index.html — fifteen minutes from nothing to a live address. When your site grows up, the files move to a local folder and the same site switches to Path B without changing a thing.
